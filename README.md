## این پروژه چیست

نکس‌یوو یک «سیستم‌عامل سازمانی» ماژولار است (Django REST + React) که برای نیازهای مختلف کسب‌وکار ماژول دارد. این مخزن **فورک مشتری «کرمان خودرو»** است و فقط بخشی از ماژول‌ها برای این مشتری فعال و کامل شده‌اند؛ بقیهٔ ماژول‌های Nexivo در کد هستن اما در لانچر نمایش داده نمی‌شوند و برای این مشتری پشتیبانی نمی‌شوند.

جریان کاری اصلی مشتری:

1. کارشناس، درخواست صدور صورت‌حساب (پرواز / هتل / ویزا / اتوبوس / قطار / گشت / تور / CIP …) ثبت می‌کند، چند فایل اکسل/همراه بار می‌کند و ردیف‌ها را در یک ادیتور جدولی نهایی می‌کند.
2. نامه با شمارهٔ `YYYY/COMPANYCODE/NNNNN` ساخته می‌شود و وارد گردش تأیید (مدیر / مدیرعامل) می‌شود.
3. پس از تأیید، **نامهٔ رسمی Word** و **صورت‌حساب PDF** تولید و در مسیر «فایل‌های تأییدشده» ذخیره می‌شوند.
4. پرداخت‌ها ثبت می‌شوند (از صفحهٔ پرداخت‌ها یا مستقیماً از ردیف صورت‌حساب) و ماندهٔ هر مشتری در «عملکرد» و «مشتریان» به‌صورت مشتق‌شده نمایش داده می‌شود.

## ماژول‌های تحویل‌شده

| کلید | عنوان | وضعیت |
|---|---|---|
| `bi_dashboard` | هوش تجاری و داشبوردها — سازنده داشبورد BI متصل به دیتابیس ERP/سوپرست + داشبورد مدیریتی ترکیبی و مالی | تحویل‌شده |
| `finance` | مالی — صورت‌حساب، پرداخت، مشتریان، عملکرد و کاردکس، خدمات | تحویل‌شده |
| `crm` | CRM — سرنخ‌ها (با کمپین)، فرصت‌ها، فعالیت‌ها، کمپین‌ها و پیامک | تحویل‌شده |
| `office` | اداری — نامه‌ها، دبیرخانه، قراردادها، کارتابل و پیوند به رکوردهای مالی | تحویل‌شده |
| `settings` | تنظیمات شرکت و برندینگ، کاربران و مجوزها، دبیرخانه‌ها، فونت‌ها و پیامک | تحویل‌شده |

لیست بالا در `frontend/src/pages/LauncherPage.tsx` با ثابت `DELIVERED_MODULES` کنترل می‌شود؛ هر ماژول جدید که بخواهد در لانچر دیده شود باید به همین مجموعه اضافه شود. ناوبری داخل ERP در `frontend/src/pages/ERPLayout.tsx` تعریف شده است (شامل پنج گروه: داشبورد، مالی، CRM، اداری، تنظیمات). تایل هوش تجاری در لانچر مستقیماً به سازنده و نمایشگر داشبوردها (`/dashboards`) پیوند دارد.

## پشتهٔ فنی

**بک‌اند**

- Python 3.11+ / Django 4.2 LTS / Django REST Framework 3.14
- PostgreSQL 15 (پیش‌فرض `psycopg2`)
- JWT دستی (`PyJWT`، `apps/accounts/authentication.py`)، بدون SimpleJWT
- Celery + Redis (تعریف‌شده؛ `CELERY_BEAT_SCHEDULE` خالی است، پس پاک‌سازی دوره‌ای فایل‌ها با cron سرور اجرا می‌شود — بخش «استقرار و عملیات»)
- Channels/Daphne برای هشدارهای realtime (اختیاری)
- تولید فایل: `python-docx` + `docxtpl` (Word)، `Jinja2` (HTML صورت‌حساب)، `WeasyPrint` و مرورگر headless (PDF)
- `jdatetime` برای تاریخ شمسی، `openpyxl`/`pandas` برای اکسل، `drf-spectacular` برای OpenAPI

**فرانت‌اند**

- React 18 + TypeScript + Vite 5
- Tailwind CSS 3 (توکن‌های برند در `tailwind.config.js` و `src/index.css`)
- Ant Design 6 برای فرم/جدول/مودال، ECharts برای نمودار، AG Grid برای جداول سنگین
- Zustand برای state، React Router 6، axios
- PWA سبک (`manifest.webmanifest`) و i18n فارسی/تقویم شمسی

## راه‌اندازی توسعهٔ محلی

### پیش‌نیازها

- Python 3.11+، Node.js 20+، npm، Git Bash (روی ویندوز)
- PostgreSQL 15 — در این نصب به‌صورت کانتینر `nexivo_db` روی پورت **۵۵۴۴** بالا می‌آید
- (اختیاری) Redis برای Celery/Channels
- (لازم برای PDF در اجرای محلی) Microsoft Edge یا Google Chrome نصب‌شده. تصویر Docker خودش Chromium را دارد و به مرورگر میزبان نیاز ندارد؛ در نبود مرورگر `WeasyPrint` استفاده می‌شود.

### گام‌به‌گام (ویندوز)

```bash
# 1) دیتابیس
docker start nexivo_db || docker run -d --name nexivo_db \
  -e POSTGRES_DB=nexivo -e POSTGRES_USER=nexivo_user -e POSTGRES_PASSWORD=nexivo_pass \
  -p 5544:5432 postgres:15

# 2) محیط پایتون
python -m venv .venv
.venv/Scripts/python.exe -m pip install -r backend/requirements.txt

# 3) متغیرهای محیطی
cp .env.example backend/.env      # سپس مقادیر واقعی را وارد کنید

# 4) مهاجرت‌ها و دادهٔ اولیه
cd backend
../.venv/Scripts/python.exe manage.py migrate
../.venv/Scripts/python.exe manage.py seed_kkt        # ادمین، دسته‌های خدمت، قالب پیش‌فرض
../.venv/Scripts/python.exe manage.py create_dev_data # کاربران نمونه (اختیاری)
cd ..

# 5) اجرا (دو ترمینال جدا)
cd backend && ../.venv/Scripts/python.exe manage.py runserver 0.0.0.0:8000
cd frontend && npm install && npm run dev -- --host 0.0.0.0   # http://localhost:3000
```

`npm run dev` روی پورت **۳۰۰۰** بالا می‌آید و `/api` و `/media` را به `http://localhost:8000` پروکسی می‌کند (`vite.config.ts`؛ با `VITE_PROXY_TARGET` قابل تغییر است).

### تست از دستگاه‌های دیگر شبکه

هر دو سرور را با `0.0.0.0` اجرا کنید تا از گوشی یا لپ‌تاپ دیگر هم باز شوند. آدرس، IP همان کارت شبکه‌ای است که دستگاه‌ها به آن وصل‌اند (مثلاً `ipconfig`):

```
http://192.168.150.121:3000/
```

API از همان پورت ۳۰۰۰ و از طریق پروکسی Vite در دسترس است؛ نیازی به باز کردن ۸۰۰۰ روی دستگاه‌های دیگر نیست. اگر صفحه باز نشد، در ویندوز اجازهٔ Inbound برای `Node.js` و `Python` در Windows Defender Firewall و Private بودن پروفایل شبکه را بررسی کنید.

روی ویندوز می‌توانید از `dev.bat` استفاده کنید: `dev.bat setup|migrate|seed|backend|frontend|dump|restore|test-backend|test-frontend`. معادل لینوکس/مک: `make` با همان تارگت‌ها (`make help`).

### ورود پیش‌فرض

`admin` / `admin12345` (از `seed_kkt` و `create_dev_data`) — **در محیط واقعی حتماً عوض شود**.

## متغیرهای محیطی

فایل `backend/.env` (نمونه در `.env.example` ریشه):

| متغیر | پیش‌فرض | توضیح |
|---|---|---|
| `SECRET_KEY` | — | کلید Django؛ در تولید الزامی و تصادفی |
| `DEBUG` | `0` | پیش‌فرض در `settings.py`؛ `.env.example` مقدار `1` می‌گذارد |
| `POSTGRES_DB` | `nexivo` | نام دیتابیس (این نصب: `kermankhodro`) |
| `POSTGRES_USER` / `POSTGRES_PASSWORD` | `nexivo_user` / `nexivo_pass` | کاربر DB |
| `DB_HOST` / `DB_PORT` | `localhost` / `5432` | آدرس DB (برای کانتینر محلی: `127.0.0.1:5544`) |
| `REDIS_URL` | `redis://redis:6379/0` | بروکر Celery و لایهٔ Channels؛ `.env.example` برای اجرای محلی `localhost:6379` می‌دهد |
| `SUPERSET_API_URL` و … | — | فقط برای BI/Superset؛ برای مشتری لازم نیست |
| `PDF_BROWSER_PATH` | — | مسیر دستی Edge/Chrome برای تولید PDF (وقتی مرورگر در مسیرهای پیش‌فرض نیست) |

- `ALLOWED_HOSTS = ["*"]` است؛ برای تولید محدود شود.
- CORS سه مبدأ `http://localhost:3000`، `http://127.0.0.1:3000` و `http://localhost:5173` را مجاز می‌کند؛ دامنهٔ تولید باید در `CORS_ALLOWED_ORIGINS` افزوده شود.
- JWT با `JWT_SECRET` (پیش‌فرض `SECRET_KEY`) و انقضای ۲۴ ساعت (`JWT_EXPIRATION_HOURS`) امضا می‌شود.

## دادهٔ اولیه و seed

- `manage.py seed_kkt` — ایدمپوتنت: کاربر `admin` با نقش `admin`، شرکت پیش‌فرض، شش دستهٔ خدمت (ویزا، اتوبوس، قطار، گشت، تور، CIP) و قالب پیش‌فرض صورت‌حساب/نامه. **روی نصب تازه اول این را بزنید.**
- `manage.py create_dev_data` — کاربران نمونه برای توسعه (نقش‌های مختلف برای تست مجوزها).
- `manage.py seed_default_modules` — ماژول‌های لانچر را همگام می‌کند.
- `manage.py purge_billing_files [--hours N]` — محتوای فایل‌های تولیدشدهٔ قدیمی‌تر از پنجرهٔ نگه‌داری (پیش‌فرض ۲۴ ساعت، `services/files.py::RETENTION_HOURS`) را پاک می‌کند. متادیتای فایل و امکان بازسازی باقی می‌ماند.

## احراز هویت و مجوزها

- ورود: `POST /api/v1/auth/login/` با `username`/`password` → `{ token }`؛ همهٔ درخواست‌ها با هدر `Authorization: Bearer <token>`.
- کلاس احراز هویت پیش‌فرض `apps.accounts.authentication.JWTAuthentication` و اجازهٔ پیش‌فرض `IsAuthenticated`.
- نقش‌ها در `accounts.User.role`؛ نقش‌های `ceo` و `admin` همیشه از ماتریس مجوز عبور می‌کنند. بقیهٔ کاربران تابع فلگ هستند.

فلگ‌های مجوز (`apps/billing/permissions.py::PERMISSION_FLAGS`):

```
can_view, can_pay, can_issue, can_manage_users, can_manage_settings,
can_delete_history, can_delete_payment, can_export, can_manage_companies,
can_submit, can_approve, can_edit_template
```

- محافظت مسیرها با دکوریتور `@perm_required("can_x")`؛ پاسخ ۴۰۱ برای کاربر ناشناس و ۴۰۳ برای نداشتن مجوز (پیام فارسی).
- فرانت مجوزهای کاربر را از `GET /api/v1/billing/me/` می‌گیرد و آیتم‌های ناوبری/دکمه‌ها را بر همان اساس نشان می‌دهد (مثلاً «صدور» فقط با `can_issue`). **در سمت سرور همیشه دوباره بررسی شود؛ هرگز به UI اعتماد نکنید.**

## دامنهٔ مالی (billing)

`apps/billing/models.py`:

| مدل | نقش |
|---|---|
| `Payer` | طرف حساب (کد یکتا، نام، نوع `legal`/`person`، `parent` برای شرکت زیرمجموعه، شناسه/کد اقتصادی، تلفن، آدرس) |
| `Invoice` | یک ردیف دفتر کل به‌ازای هر فایل تولیدشده: payer_code، نوع خدمت، شماره نامه، مبلغ، تاریخ صدور، مسیر فایل و فیلدهای ابطال (`reversed_at`/`reversed_by`/`reversal_reason`). ردیف ابطال‌شده باقی می‌ماند و در مانده حساب نمی‌شود |
| `BillingAuditEntry` | ردپای ابطال و حذف ردیف‌های مالی: موجودیت، شناسه، عملیات، دلیل، تصویر کامل رکورد و کاربر |
| `AuditLog` (apps.audit_log) | ایجاد/ویرایش/حذف `Invoice`، `Payment`، `ManualDebt`، `Credit` و `ApprovalRequest` با کاربر انجام‌دهنده (پس از احراز هویت JWT)؛ چون این ردیف‌ها شرکت ندارند، `GET /audit/entries/` آن‌ها را برای کاربران دارای مجوز `can_view` صورت‌حساب در کنار ردیف‌های شرکت خودشان نشان می‌دهد و ردیف شرکت‌های دیگر را لو نمی‌دهد |
| `Payment` | پرداخت: payer، مبلغ، تاریخ، شماره پیگیری، توضیح، `created_at` (فیلد «سازنده» وجود ندارد) |
| `ManualDebt` | بدهی دستی (بدون صورت‌حساب) |
| `Credit` | بستانکاری/اعتبار |
| `LetterSequence` / `AvailableLetterNumber` | شماره‌گذاری نامه و شماره‌های آزادشده |
| `ApprovalRequest` | درخواست صدور + وضعیت گردش تأیید + payload ردیف‌ها |
| `FinalFile` | فایل تولیدشده: دو نسخه (BLOB در `file_data` + مسیر روی دیسک)، `purged_at` پس از پنجرهٔ نگه‌داری |
| `ServiceCategory` | دستهٔ خدمت (نام فارسی، کد، ترتیب) |
| `InvoiceTemplate` | قالب قابل ویرایش صورت‌حساب/نامه (HTML/Word) |
| `CompanySettings` | تک‌رکورد: نام/شناسه/آدرس/تلفن، دو حساب بانکی + شبا، لوگو، امضا، مهر، نام و سمت مدیر، سه قالب Word (اصلی/زیرمجموعه/بستانکاری)، پانویس قانونی، مسیر ذخیرهٔ فایل تأییدشده |

### مانده: همیشه مشتق‌شده

هیچ فیلد ذخیره‌شده‌ای برای مانده وجود ندارد. `services/balance.py` مانده را از دفتر کل محاسبه می‌کند:

```
مانده = مبلغ صورت‌حساب‌ها + بدهی‌های دستی − پرداخت‌ها − بستانکاری‌ها
```

نتیجه در سه جا یکسان است: `Payer` در فهرست، اندپوینت `payers/<code>/balance/` و صفحهٔ عملکرد. **قاعده:** هیچ‌وقت مانده را در مدل ذخیره/کش نکنید؛ هر تغییر در فرمول باید در `balance.py` باشد و تست `test_invoice_row_payment_lowers_balance_and_keeps_the_invoice` را به‌روز کند.

### پرداخت از ردیف صورت‌حساب

دکمهٔ پرداخت روی هر ردیف صورت‌حساب همان `POST /api/v1/billing/payments/` را صدا می‌زند (با شمارهٔ نامه به‌عنوان مرجع). فقط یک دفتر کل وجود دارد؛ بنابراین پرداخت فوراً در مانده و در فهرست پرداخت‌ها دیده می‌شود و صورت‌حساب هم حذف/پنهان نمی‌شود (صورت‌حساب پرداخت‌شده در فهرست می‌ماند و با فیلتر خدمت/وضعیت قابل جداسازی است).

## شماره‌گذاری نامه و گردش تأیید

- شمارهٔ نامه: `YYYY/COMPANYCODE/NNNNN` (مثال `1404/8200/00001`)، تولید در `services/numbers.py` و ارسال از `GET /billing/next-letter/`.
- گردش: `pending` → `approve` (فایل‌ها ساخته می‌شوند) یا `reject` (شماره آزاد می‌شود). `approval_approve` فایل‌ها را در `FinalFile` ثبت و در مسیر «فایل‌های تأییدشده» (`CompanySettings.approved_output_path` یا `MEDIA_ROOT/approved`) ذخیره می‌کند.
- دسترسی: خواندن `can_view`، ثبت `can_submit`، تأیید `can_approve`. صف‌ها: `GET /billing/approvals/pending/` (با `can_view`) و `GET /billing/approvals/mine/` (با `can_submit`).
- دانلود نامه: `GET /billing/files/<id>/download/` یا `GET /billing/files/by-letter/<letter_number>/` (برای ردیف‌هایی که فایل با شناسه ندارند). بازسازی: `POST /billing/files/<id>/regenerate/`.

## تولید فایل: Word و PDF

`apps/billing/services/generation.py`

1. **نامه = Word (`.docx`)** — قالب Word آپلودی شرکت (سه قالب: اصلی، زیرمجموعه، بستانکاری) با placeholderهای `{{ }}` و `docxtpl`؛ اگر قالبی آپلود نشده باشد، همان نامه به‌صورت برنامه‌ای با `_render_programmatic_docx` ساخته می‌شود (پوشهٔ `services/templates/` وجود ندارد). لوگو/امضا/مهر و اطلاعات شرکت تزریق می‌شوند.
2. **صورت‌حساب = PDF** — از HTML ساخته می‌شود (`INVOICE_HTML` + `INVOICE_CSS` با Jinja)، نه از Word:
   - A4 افقی، جهت RTL، اعداد فارسی. فونت **Vazirmatn داخل خود PDF جاسازی می‌شود** (دو زیرمجموعهٔ arabic و latin با وزن ۴۰۰/۷۰۰ از `services/assets/`، مجوز SIL OFL)؛ بنابراین خروجی روی هر ماشینی یکسان است و به نصب B Nazanin یا Tahoma وابسته نیست. B Nazanin همچنان در نامهٔ Word استفاده می‌شود، چون آن را Word روی سیستم کاربر رندر می‌کند.
   - عرض ستون‌ها با `<colgroup>` ثابت است (ردیف ۵٪، قرارداد ۹٪، مسافر ۱۶٪، شرح خدمات ۲۰٪، تاریخ ۱۰٪، توضیحات ۱۲٪، بدهکار ۱۰٪، بستانکار ۸٪، مانده ۱۰٪) و `overflow-wrap: anywhere` باعث می‌شود نام‌های طولانی در همان سلول بشکنند و جدول از حاشیهٔ صفحه بیرون نزند.
   - هدر: لوگو، تاریخ، شمارهٔ صورت‌حساب؛ عنوان «صورت حساب {نوع خدمت} {شرکت}»
   - جدول ۹ ستونی، **۸ ردیف در هر صفحه**، **جمع هر صفحه** و **جمع کل** در پایان
   - فوتر: محل امضا، مهر و نام/سمت مدیر؛ لوگو/امضا/مهر به‌صورت data-URI تزریق می‌شوند
   - نکتهٔ مهم Jinja: استایل‌شیت با `{{ css|safe }}` درج می‌شود؛ اگر `safe` حذف شود، فاصله‌گذاری HTML کوتیشن‌های `font-family` را به `&#39;` تبدیل می‌کند، کل اعلان فونت بی‌اثر می‌شود و خروجی بی‌صدا با فونت پیش‌فرض (Times New Roman) چاپ می‌شود. تست `test_stylesheet_is_not_html_escaped` مراقب این رگرسیون است.
   - موتور PDF: یک پروسهٔ headless Edge/Chrome که **برای هر درخواست فقط یک‌بار** بالا می‌آید (`PdfBrowser` در همان فایل، با پروتکل DevTools) و همهٔ صورت‌حساب‌های آن درخواست را چاپ می‌کند؛ یک تأیید سه‌خدمتی با سه ردیف PDF در حدود ۴ ثانیه تمام می‌شود. فقط وقتی هیچ مرورگری پیدا نشود `WeasyPrint` استفاده می‌شود؛ اگر مرورگر موجود باشد ولی بالا نیاید یا چاپ را برنگرداند، `GenerationError` با پیام فارسی پرتاب و در `generation_error` درخواست ثبت می‌شود (دیگر به‌صورت خاموش به WeasyPrint برنمی‌گردد).
3. ستون‌ها بر اساس نوع خدمت نگاشت می‌شوند: پرواز (مسیر/تاریخ پرواز/`بلیط: …`)، هتل (هتل + نوع اتاق، بازهٔ ورود و خروج، نفرات)، سایر خدمات (شرح خدمات/تاریخ/توضیحات).
4. پس از پنجرهٔ نگه‌داری، فقط payload فایل پاک می‌شود؛ `regenerate_file` همان ورودی ذخیره‌شده را دوباره می‌سازد (Word و PDF هر دو).

> نکته: قالب قابل ویرایش (`InvoiceTemplate`) فقط روی **متن نامه** اثر دارد، نه روی صورت‌حساب. پیش‌نمایش `POST /billing/templates/active/preview/` (با مجوز `can_edit_template`) همان HTML نامه را با قالب فعال می‌سازد و برای نمایش در مرورگر، آن را از همان مسیر تولید PDF صورت‌حساب (`html_to_pdf`، یعنی Chromium/WeasyPrint) به PDF تبدیل می‌کند؛ این فقط یک پیش‌نمایش است. **PDF واقعی صورت‌حساب همیشه از `INVOICE_HTML`/`INVOICE_CSS` ثابت ساخته می‌شود** و قالب آپلودی هیچ اثری روی آن ندارد.

## ماژول اداری (Office)

اپ `apps/office` با ماژول `office` در `Company.enabled_modules`. داده‌های Office (نامه، گیرنده، ارجاع، یادداشت، شماره‌گذاری) جداست و هیچ کلید خارجی به `finance`/`crm` ندارد؛ پیوند با `(entity_type, source_record_id)` در `OfficeBusinessLink` انجام می‌شود و خواندن مالی از `apps/office/business.py` (فقط خواندن) است.

- **شماره‌گذاری:** `YYYY/SECRETARIAT/TYPE/NNNNN` (مثال `1405/CEN/O/000001`)، سال از تاریخ شمسی نامه. تخصیص داخل تراکنش با `select_for_update` روی `SecretariatNumberSequence`؛ شمارهٔ ثبت‌شده تغییرناپذیر و بایگانی/لغو آزادکنندهٔ شماره نیست.
- **گردش:** پیش‌نویس → ثبت (دبیرخانه؛ فقط عضو با حق ثبت یا مدیر/CEO) → ارجاع/اقدام → پاسخ → بایگانی. دیدن نامه (`read_at`) از اقدام (`route_status`) جدا است.
- **دسترسی:** شرکت + گیرنده/ارجاع/مسئول/سازنده؛ مدیر و CEO همهٔ نامه‌های شرکت را می‌بینند؛ نامهٔ «خیلی محرمانه/محدود» فقط برای افراد پیوسته.
- **پنل مالی:** مشتری، صورت‌حساب، رسید، پرداخت و فرصت CRM با مقدار تازه از منبع، مبالغ فقط برای نقش مالی/مدیر؛ در نبود رکورد، وضعیت «در دسترس نیست» و در خطای منبع، خطای کنترل‌شده.
- **اعلان:** ثبت، ارجاع و پاسخ یک ردیف در فید `Notification` می‌سازد.
- **API:** پیشوند `/api/v1/office/` — جزئیات و محدودیت‌ها در `docs/OFFICE/README.md`.
- **دامنهٔ فعلی:** مدیریت اسناد، تقویم، جلسات و ارتباطات سازمانی در نسخه‌های بعدی؛ وظیفهٔ CRM تکرار نشده است.

## پیش‌نمایش پیوست‌ها

پیش‌نمایش پیوست‌های نامهٔ اداری در یک مودال مشترک (`frontend/src/components/document-preview/`) انجام می‌شود و فایل **هرگز از URL عمومی** خوانده نمی‌شود: کامپوننت با همان API دانلود احراز‌هویت‌شده یک `Blob` می‌گیرد، `objectURL` می‌سازد و هنگام بستن آن را `URL.revokeObjectURL` می‌کند.

| نوع فایل | نمایشگر | کتابخانه |
|---|---|---|
| PDF | نمایشگر بومی مرورگر از `blob:` (زوم/جست‌وجو/چاپ خود مرورگر) | بدون کتابخانه — فایل احراز‌هویت‌شده به Blob تبدیل می‌شود |
| تصویر (PNG/JPEG/WebP/GIF) | viewer داخلی با زوم/چرخش | خود مرورگر |
| DOCX | فقط‌خواندنی، بدون ویرایش | `@casualoffice/docs@1.4.2` (MIT) در حالت `mode="viewing"` و `React.lazy` |
| XLSX | تب هر Sheet + جدول فقط‌خواندنی (حداکثر ۵۰۰ ردیف اول برای سرعت) | `xlsx@0.18.5` (Apache-2.0) |
| CSV/TSV | جدول ساده‌شده | viewer داخلی |
| TXT/LOG | متن با فونت یکنواخت | viewer داخلی |
| سایر | پیام «پیش‌نمایش پشتیبانی نمی‌شود» + دکمهٔ دانلود | — |

- **امنیت:** دکمهٔ پیش‌نمایش فقط برای کاربری است که اجازهٔ دیدن نامه را دارد؛ دانلود سمت سرور همچنان `X-Content-Type-Options: nosniff`، `Content-Security-Policy: default-src 'none'; sandbox` و `X-Frame-Options: DENY` دارد. پارامتر `?inline=1` در `GET /api/v1/office/correspondence/<id>/attachments/<attachment_id>/download/` فقط `Content-Disposition` را از `attachment` به `inline` تغییر می‌دهد و بقیهٔ بررسی‌های دسترسی سر جای خود است.
- **خطا:** فایل خراب/رمزدار پیام فارسی و دکمهٔ دانلود نشان می‌دهد؛ خطای رندر DOCX با Error Boundary گرفته می‌شود تا کل صفحه سفید نشود.
- DOCX و XLSX به‌صورت lazy بارگذاری می‌شوند تا حجم بستهٔ اولیه بالا نرود.
- **فونت‌های سازمان:** در `/erp/settings` → تب «فونت‌های اسناد» فونت‌های سری B (B Nazanin، B Titr و…) آپلود می‌شوند؛ نام فونت باید همان نام داخل فایل Word باشد. سیستم آن‌ها را به‌صورت `@font-face` تزریق می‌کند و DOCX/XLSX/CSV/TXT با همان فونت رندر می‌شوند (`/api/v1/auth/fonts/`).
- **IDM و دانلودمنیجرها:** پیش‌نمایش PDF از `blob:` استفاده می‌کند، پس افزونهٔ IDM درخواستی برای گرفتن فایل نمی‌بیند؛ اگر IDM روی مرورگر فعال است و صفحه را می‌دزدد، `localhost` را در تنظیمات IDM مستثنی کنید.

## داشبورد مدیریتی و مالی

بخش داشبورد شامل دو نمای اختصاصی و یکپارچه است:

- `/erp` یا `/erp/billing` — **داشبورد مالی**:
  - ۴ کارت شاخص کلیدی: جمع صورت‌حساب‌ها، جمع پرداخت‌ها، اعتبار (بستانکاری) و مانده وصول‌نشده.
  - **نمودار روند ماهانه صدور و دریافت‌ها (دوره ۱۲ ماهه):** یک نمودار دوگانهٔ شیب‌دار (Dual Area Gradient) بر پایه رنگ اصلی و ثانویه سازمان، مقایسه صدور صورت‌حساب‌ها با دریافت‌های وصول‌شده در ۱۲ ماه گذشته با فونت وزیرمتن و ارقام فارسی.
  - **نمودار ۱۰ شرکت با بیشترین بدهی پرداخت‌نشده:** نمودار دایره‌ای با پدینگ زاویه‌ای (`pie-padAngle`) که رتبه‌بندی بدهکاران را بر اساس **مانده حساب خالص واقعی** (`بدهکاری منهای پرداختی‌ها و بستانکاری‌ها`) نمایش می‌دهد و بدهی ناخالص قبل از پرداخت را منظور نمی‌کند. کلیک روی هر قاچ یا ردیف لیست، پنجره کاردکس تفصیلی شرکت را باز می‌کند.
  - **صورت‌حساب به تفکیک خدمت:** نمودار دایره‌ای شامل ۵ خدمت برتر و تجمیع باقی خدمات در قاچ ششم («باقی خدمات»).
- `/erp/management` — **داشبورد مدیریتی ترکیبی**:
  - ۸ کارت KPI فراگیر از ماژول‌های مالی، CRM، اداری و پرسنلی.
  - نمودار میله‌ای مقایسه‌ای مالی ۶ ماهه و نمودار دایره‌ای ترکیب فعالیت سازمان.
  - نمودار دونات ۱۰ بدهکار برتر با اتصال تعاملی به کاردکس حساب.
  - هدر تمیز و مدیریتی بدون برچسب‌های اضافی سیستمی.

## پنجره کاردکس و عملکرد مشتریان (Ledger Modal)

برای هر طرف حساب، یک پنجرهٔ جامع تحلیل گردش حساب و کاردکس (`frontend/src/pages/billing/PayerStatementModal.tsx`) تعبیه شده است:

- **نحوهٔ دسترسی:** با کلیک روی هر قاچ از نمودارهای دایره‌ای ۱۰ بدهکار برتر (در داشبورد مالی یا مدیریتی)، کلیک روی ردیف‌های لیست بدهکاران، یا کلیک روی هر شرکت در جداول صفحه عملکرد (`/erp/billing/performance`).
- **اطلاعات سربرگ:** نام شرکت، شناسه ملی، کد اقتصادی، شماره تماس و آدرس ثبت‌شده.
- **شاخص‌های خلاصه:** ۴ کارت شامل جمع بدهی (صورت‌حساب‌ها + بدهی دستی)، جمع واریزی‌ها و بستانکاری، مانده خالص نهایی، و تعداد کل تراکنش‌ها.
- **جدول ریز تراکنش‌های زمانی:** کلیه اسناد (صورت‌حساب، بدهی دستی، پرداخت، اعلامیه بستانکاری) به ترتیب تاریخ با نمایش تاریخ جلالی، نوع سند (با بج‌های رنگی)، شماره مرجع/عطف، شرح سند، ستون‌های بدهکار، بستانکار و مانده خط‌به‌خط.
- **فیلتر و جستجو:** فیلتر آنی بر اساس نوع سند و جستجوی متنی روی شرح و شماره مرجع.
- **خروجی اکسل:** دکمه دانلود مستقیم کاردکس اکسل که ریز کامل تراکنش‌ها را در **برگه اول (Sheet 1)** فایل اکسل قرار می‌دهد.

## هوش تجاری و یکپارچه‌سازی با Superset (BI)

پلتفرم به یک موتور هوش تجاری هیبرید (Headless Superset + PostgreSQL Data Engine) مجهز است:

- **مسیر اختصاصی داشبوردها (`/dashboards`):** تایل «هوش تجاری» در صفحه اصلی مستقیماً به محیط سازنده و نمایشگر چندصفحه‌ای داشبوردها (`DashboardListPage` و `DashboardBuilderPage`) متصل است و ویجت‌های تعاملی را روی شبکهٔ منعطف با ECharts رندر می‌کند.
- **اتصال دیتابیس ERP جاری به عنوان مجموعه داده‌ها:**
  ۱۰ جدول کلیدی سازمان در پایگاه‌داده PostgreSQL به عنوان Datasetهای فعال شناسایی و ثبت شده‌اند:
  - `billing_invoice` (صورت‌حساب‌ها)
  - `billing_payment` (دریافت‌ها و پرداخت‌ها)
  - `billing_payer` (مشتریان و طرف‌های حساب)
  - `billing_manualdebt` (بدهی‌های دستی)
  - `billing_credit` (اعلامیه‌های بستانکاری)
  - `office_contract` (قراردادها)
  - `office_correspondence` (مکاتبات اداری)
  - `crm_opportunity` (فرصت‌های فروش)
  - `crm_lead` (سرنخ‌ها)
  - `crm_campaign` (کمپین‌ها)
- **اعمال دسترسی و سطوح عملیاتی کاربران:**
  - دسترسی نقشی (`allowed_roles`) در سطح هر مجموعه داده کنترل می‌شود (مثلاً جداول مالی فقط برای مدیرعامل، ادمین و مالی).
  - مجوز عملیاتی `can_view` در کلیه کوئری‌های تجمیعی بررسی شده و کاربران فاقد مجوز دسترسی ندارند.
  - امنیت در سطح سطر (RLS) و تخصیص داشبورد (`DashboardAssignment`) فیلترهای داده‌ای را به صورت خودکار روی کوئری‌ها اعمال می‌کند.
- **دستور مدیریتی و رابط وب:**
  - دستور `python manage.py sync_erp_datasets` جهت شناسایی اسکیما و همگام‌سازی جداول ERP در `backend/apps/datasets/services.py`.
  - صفحهٔ وضعیت سوپرست (`/admin/superset`) با دکمه اختصاصی «شناسایی و اتصال جداول دیتابیس ERP» و بررسی سلامت اتصال کلاینت سوپرست (`superset.py::ensure_database_registered`).
- **جدول محوری ماتریسی (Looker Studio Pivot Table):**
  - امکان تعریف دو بعد متقاطع: **بُعد سطرها** (مثلاً مشتریان `payer_name`) و **بُعد ستون‌ها** (مثلاً نوع خدمت `invoice_type`).
  - تبدیل خودکار مقادیر یکتای بعد ستون به سرستون‌های افقی پویا (پرواز، هتل، قطار، خدمات فرودگاهی و...).
  - تجمیع متقاطع بر اساس تابع دلخواه (`COUNT` جهت شمارش تعداد فاکتورها/خدمات، `SUM` جهت جمع مبالغ، `AVG`، `MIN`، `MAX`).
  - محاسبه و نمایش ستون **جمع کل هر سطر** و سطر **جمع کل هر ستون** (Grand Total) به همراه نوار جستجوی زنده در سطرها و اعداد فارسی.
- **کوئری و فرمول SQL سفارشی (کاربر حرفه‌ای):**
  - ادیتور اختصاصی دستورات SQL جهت نوشتن محاسبات، فیلترها و فرمول‌های پیچیده با پشتیبانی از `SELECT` و `WITH`.
  - اعتبارسنجی امنیتی پیشگیرانه در بک‌اند (`_validate_safe_select_sql`) جهت ممانعت از اجرای دستورات مخرب یا تغییردهنده داده.
  - دکمهٔ «تست کوئری» جهت پیش‌نمایش سریع تعداد سطرها، زمان اجرا و ستون‌های خروجی در پنل تنظیمات.
- **فرمول محاسباتی ترکیبی KPI (Dual-Metric Math Formula):**
  - محاسبهٔ آنی بین دو شاخص مجزا (مانند مانده = بدهکاری - دریافتی، درصد وصول = (دریافتی / کل) × ۱۰۰، نسبت و فرمول دلخواه).
  - نمایش تفکیک مقادیر شاخص اول و دوم در زیر کارت KPI به همراه فرمت‌بندی سه رقم سه رقم و فونت وزیرمتن.
- **طراحی بهینه و خلوت پای‌چارت و دونات (مشابه Google Data Studio):**
  - محدودسازی هوشمند قاچ‌ها (پیش‌فرض ۱۰ مورد برتر) و تجمیع مقادیر باقیمانده در قاچ «سایر» جهت جلوگیری از شلوغی و تداخل برچسب‌ها.
  - استایل دونات مدرن با انحنای گوشه‌ها (`borderRadius: 8`)، فاصله تمیز بین برش‌ها (`padAngle: 3`) و پالت رنگی هماهنگ.
- **پنل تنظیمات تب‌بندی‌شده و ارگونومیک ویجت‌ها (Drawer UI):**
  - ساختار دو زبانه‌ای منظم مشابه Looker Studio: زبانه **«تنظیمات داده»** (عنوان، نوع نمودار، منبع داده، Pivot Table، فیلترها، کوئری SQL و مرتب‌سازی) و زبانه **«ظاهر و استایل»** (پالت رنگ، رنگ سری‌ها/برش‌ها، فرمت عدد KPI، سبک کارت، تصویر پس‌زمینه و قالب‌بندی شرطی).
  - فوتر ثابت و پین‌شده در پایین پنل (Pinned Footer) با دکمه‌های «ذخیره تنظیمات» و «انصراف» به صورت دائمی در دسترس بدون نیاز به اسکرول منو.
- **قفل امنیتی چینش و طراحی داشبورد با پسورد اختصاصی مدیر (Admin Design Password Lock):**
  - امکان قفل کردن کامل ساختار و دیزاین داشبورد با رمز عبور اختصاصی مدیر ارشد (`is_design_locked` و `design_password_hash` هش‌شده با `make_password`).
  - جلوگیری قطعی از دستکاری چینش، جابه‌جایی، تغییر اندازه، افزودن/حذف نمودار و صفحات توسط سایر کاربران، **حتی مدیرعامل**؛ دسترسی تغییرات تنها با ورود رمز اختصاصی باز می‌شود.
  - گیت محافظتی سمت سرور (Backend Guard) روی کلیه اندپوینت‌های ویرایش ویجت، چیدمان و صفحات (`layout/`, `widgets/`, `pages/`) با بازگرداندن وضعیت `423 Locked`.
  - مودال مدیریتی قفل (`DesignLockModal`) با قابلیت بازگشایی موقت در نشست فعال کارشناس (`sessionUnlocked`) و ارسال هدر امنیتی `X-Design-Password` روی درخواست‌های مجاز.
  - امکان قفل مجدد سریع، تغییر رمز عبور و یا حذف دائمی قفل طراحی توسط مدیر.

## برندینگ، متادیتا و هماهنگی دستگاه‌های iOS

- **نام سازمان و متادیتای سیستم:**
  در تنظیمات برندینگ (`BrandingTab`) امکان ویرایش مستقیم نام سازمان اضافه شده است. با ذخیرهٔ نام سازمان، متادیتاهای مرورگر و وب‌کارت سیستم شامل `document.title`، `meta[name="apple-mobile-web-app-title"]` و `meta[name="application-name"]` در لحظه به‌روزرسانی می‌شوند تا نام برنامه در آیفون، آیپد و شورت‌کات‌های دستکتاپ یکپارچه و یکسان باشد.
- **لوگوی سازمانی در Favicon و Apple Touch Icon:**
  در `frontend/src/store/brandingStore.ts`، لوگوی شرکت با نسبت ابعاد مناسب روی بوم شفاف ۱۹۲×۱۹۲ پیکسل رندر شده و تگ‌های `link[rel="apple-touch-icon"]`، `link[rel="icon"]` و `meta[name="apple-mobile-web-app-title"]` به صورت داینامیک تنظیم می‌شوند.
- **جلوگیری از فلش لوگو و نام پیش‌فرض:**
  در `index.html`، اسکریپت اولیه به صورت همگام لوگو و نام سازمان را از کش `localStorage` می‌خواند تا در آیکون Home Screen دستگاه‌های iOS، تب‌های سافاری و مرورگرها هیچ‌گونه لوگو یا نام پیش‌فرض نکس‌یوو دیده نشود.
- **اصلاح کنتراست و تم روشن/تیره:**
  بخش‌های تنظیمات برندینگ و سربرگ نامه (`BillingLetterheadTab`) که دارای پس‌زمینه‌های تیره و تضاد نامناسب در حالت لایت‌مود بودند، با استفاده از کلاس‌های طراحی تطبیقی (`bg-white dark:bg-nx-navy` و `text-slate-900 dark:text-white`) بازنویسی و تمیز شدند.

## پیامک (SMS)

زیرسامانهٔ پیامک داخل CRM برای ارسال به مشتری/سرنخ و اتصال به کمپین.

- **مدل‌ها (`apps/crm/models.py`):**
  - `SmsSettings` — تنظیمات هر شرکت: `provider` (`kavenegar` / `niksms` / `generic`)، `sender`، `api_key`، `username`/`password` (نیک‌اس‌ام‌اس)، `endpoint` (سرویس سفارشی) و `enabled`.
  - `SmsMessage` — لاگ هر تلاش ارسال: شمارهٔ نرمال‌شده، متن، ارائه‌دهنده، وضعیت `sent`/`failed`، شناسهٔ پیام ارائه‌دهنده، خطا و کمپین مرتبط.
- **ارائه‌دهنده‌ها (`apps/crm/sms.py`):** کاوه‌نگار (`/sms/send.json`)، نیک‌اس‌ام‌اس (`PostSmsWithApiKey`) و سرویس سفارشی (POST JSON با `Authorization: Bearer`). شمارهٔ موبایل با تبدیل ارقام فارسی/عربی و `+98`/`0098` نرمال می‌شود. خطای شبکه/HTTP به `SmsError` فارسی تبدیل می‌شود.
- **API:**

| متد و مسیر | کار | دسترسی |
|---|---|---|
| `GET /api/v1/crm/sms/settings/` | خواندن تنظیمات؛ پاسخ فقط `has_api_key`/`has_password` می‌دهد، نه مقدار کلید | کاربر CRM؛ `can_manage` برای ویرایش |
| `PUT/PATCH /api/v1/crm/sms/settings/` | ذخیرهٔ تنظیمات؛ فیلد خالی کلید/رمز، مقدار قبلی را حفظ می‌کند | مدیر سیستم/مدیرعامل یا `can_manage_settings` |
| `POST /api/v1/crm/sms/send/` | ارسال: `{phone, message, campaign_id?}`؛ شمارهٔ ۱۱ رقمی، متن ۱ تا ۱۰۰۰ کاراکتر | کاربر CRM |
| `GET /api/v1/crm/sms/messages/` | ۱۰۰ پیامک آخر با وضعیت و خطا | کاربر CRM |

- **رفتار:** اگر درگاه `enabled` نباشد ارسال با ۴۰۰ و پیام «فعال نیست» رد می‌شود؛ خطای ارائه‌دهنده ۵۰۲ برمی‌گرداند و همان رکورد با `status=failed` و متن خطا در تاریخچه می‌ماند. ارسال موفق شناسهٔ ارائه‌دهنده را ذخیره می‌کند.
- **رابط کاربری:** `/erp/crm/sms` (ارسال، تاریخچه) و تب «تنظیمات پیامک» در `/erp/settings`؛ هر دو از کارت مشترک `frontend/src/components/SmsSettingsPanel.tsx` استفاده می‌کنند.
- **کمپین در سرنخ:** `Lead.campaign` (FK اختیاری به `Campaign`) اضافه شده و فرم «سرنخ جدید» یک select «کمپین (برای رهگیری)» دارد؛ `campaign_id` سمت سرور به شرکت محدود می‌شود و `campaign_name` در فهرست سرنخ‌ها نمایش داده می‌شود.
- **مهاجرت:** `crm/0002_smssettings_smsmessage` و `crm/0003_lead_campaign`.

**برد فرصت‌ها (CRM):** صفحهٔ `/erp/crm/opportunities` دو نما دارد: «برد» (پیش‌فرض) و «فهرست». برد، فرصت‌های باز را در چهار ستون `prospecting / qualification / proposal / negotiation` نشان می‌دهد و هر ستون تعداد و جمع ارزش تخمینی را دارد. جابه‌جایی کارت با کشیدن و رها کردن، `POST /api/v1/crm/opportunities/<id>/move/` را صدا می‌زند؛ این endpoint فقط وضعیت‌های باز را می‌پذیرد، فرصت بسته را جابه‌جا نمی‌کند و بستن معامله را به `close-won`/`close-lost` می‌سپارد تا تاریخ بستن و احتمال درست ثبت شود. هر جابه‌جایی برای مشتریِ متصل، یک رویداد `status_changed` در `CustomerTimeline` می‌سازد. فرصت‌های برده/باخته در دو کارت خلاصه زیر برد دیده می‌شوند. کلیک روی کارت (یا نام فرصت در فهرست) پنل رکورد فرصت را باز می‌کند: جزئیات مالی، فعالیت‌ها و وظایف همان فرصت با امکان ثبت فعالیت/وظیفه و تکمیل آن‌ها. این پنل از فیلتر `?opportunity=<id>` روی `GET /api/v1/crm/activities/` و `GET /api/v1/crm/tasks/` استفاده می‌کند.

**قواعد چرخهٔ فرصت:** `status` منبع حقیقت قیف است و `stage` از آن مشتق می‌شود (`prospecting→lead`, `qualification→qualified`, `proposal→proposal_sent`, `negotiation→verbal_agreement`, بسته→closed) تا برد و داشبورد CRM یک عدد نشان دهند. `PUT /opportunities/<id>/` دیگر `status`/`stage` را نمی‌پذیرد (۴۲۲) و تغییر وضعیت فقط از `move/` یا `close-won/`/`close-lost/` انجام می‌شود. ثبت فعالیت/وظیفه فقط `opportunity_id` را می‌پذیرد و مالکیت آن را با شرکت بررسی می‌کند؛ کلیدهای خام FK نادیده گرفته می‌شوند. دکمهٔ «فقط فرصت‌های من» برد را بر اساس `assigned_to` کاربر فیلتر می‌کند.
| `/erp/settings`, `/erp/settings/users` | تنظیمات شرکت، کاربران/مجوزها، دبیرخانه‌ها و تنظیمات پیامک |
| `/erp/profile` | تنظیمات کاربری (مشخصات، آواتار، رمز عبور، تم) |

بقیهٔ مسیرهای ERP (finance/inventory/sales/…) از Nexivo باقی مانده‌اند و برای این مشتری در ناوبری نیستند؛ در صورت نیاز به فعال‌سازی، ابتدا مالکیت داده و مجوزها را مشخص کنید.

### چیدمان و تجربهٔ کاربری

- `ERPLayout.tsx` سایدبار دسکتاپ را فقط از `lg` به بالا نشان می‌دهد.
- **موبایل:** نوار پایین با سه مقصد (داشبورد، صورت‌حساب، میزکار اداری) + «منو» و دکمهٔ شناور «ثبت جدید» در وسط نوار. دکمهٔ همبرگری در هدر وجود ندارد؛ «کاربران» فقط از تنظیمات در دسترس است. «منو» یک **کارت** از پایین باز می‌کند (ترنسفورم inline، `translateY(115%) → 0`، ۳۰۰ms) با دستگیره، عنوان، دکمهٔ بستن و ردیف‌های بزرگ (متن ۱۵–۱۶px، آیکون ۳۶px، هایلایت آیتم فعال). با انتخاب آیتم، کارت پایین می‌رود و بعد از همان ۳۰۰ms صفحه باز می‌شود (`SHEET_TRANSITION_MS`). وقتی کارت بسته است `inert` می‌شود تا فوکوس روی ردیف‌های نامرئی نرود.
- تم روشن/تیره با کلاس `dark` روی `html`. برای کارت‌های همیشه‌تیره (پوستهٔ نفتی) از کلاس `dark-surface` استفاده کنید تا متن سفید داخلشان با قاعدهٔ سراسری `html:not(.dark) .text-slate-600` دچار کنتراست پایین نشود.
- لودینگ زیرمنوها (Suspense در `App.tsx`) لوگوی **برند** را نشان می‌دهد (`useBrandLogo`)؛ لوگوی Nexivo فقط fallback پیش‌فرض است.
- `CARD` مشترک صفحات مالی در `src/pages/billing/shared.ts` است؛ ظاهر کارت‌ها را از آنجا تغییر دهید، نه تک‌تک صفحات.
- PWA: `manifest.webmanifest` + آیکن‌ها؛ نصب روی موبایل پشتیبانی می‌شود.
- **منوی حساب:** فقط دو گزینه دارد — «تنظیمات کاربری» (`/erp/profile`) و «خروج از سامانه»؛ ویرایش پروفایل، آواتار و رمز در همان صفحه است، نه در مودال‌های هدر.

## استقرار و عملیات

- `docker-compose.yml`: postgres، redis، superset، backend، frontend برای محیط توسعه/نمایش.
- `docker-compose.prod.yml`: نسخهٔ تولید (Gunicorn + Nginx/Vite build). پیش از استقرار: `DEBUG=0`، `SECRET_KEY` تصادفی، دامنه در `ALLOWED_HOSTS` و `CORS_ALLOWED_ORIGINS`، سرو `media/` و بکاپ دیتابیس.
- **بکاپ/بازیابی:** `make dump` / `make restore FILE=backups/x.sql` (ویندوز: `dev.bat dump|restore`). قبل از هر مهاجرت سنگین یک dump بگیرید.
- **فایل‌های تولیدی:** در `MEDIA_ROOT/approved` (یا مسیر تنظیمات). حجم را کنترل کنید؛ `purge_billing_files` را روزانه در cron بگذارید: `0 3 * * * python manage.py purge_billing_files --hours 24`.
- **فونت:** لازم نیست هیچ فونتی روی سرور نصب باشد؛ Vazirmatn (OFL) در `services/assets/` همراه کد است و به‌صورت base64 داخل CSS صورت‌حساب جاسازی می‌شود. فقط برای نامهٔ Word، نصب B Nazanin روی سیستم کاربر نهایی لازم است (در Docker فونت لازم نیست).
- **مرورگر headless:** `_find_pdf_browser` اول `PDF_BROWSER_PATH` و سپس مسیرهای ویندوز/لینوکس Edge و Chrome را می‌گردد؛ روی مک مسیر bundle (`/Applications/…`) در فهرست نیست، پس باید `PDF_BROWSER_PATH` را ست کرد. `--headless=new` نیاز به Chrome/Edge نسخهٔ ۱۱۲ به بالا دارد. کتابخانهٔ `websocket-client` کلاینت CDP است و در `requirements.txt` آمده است. در هر پروسهٔ Gunicorn فقط یک مرورگر همزمان بالا می‌آید (`_browser_lock` در `generation.py`): درخواست دوم تا بسته‌شدن مرورگر اول صبر می‌کند و اگر تا پایان مهلت مرورگر (`timeout`، پیش‌فرض ۹۰ ثانیه) نوبتش نرسد، خطای فارسی ثبت می‌شود؛ هر worker پروسهٔ جدا و قفل خودش را دارد.
- **تصویر Docker:** `backend/Dockerfile` دو مرحله‌ای است. مرحلهٔ builder فقط `gcc`/`libpq-dev` را برای نصب پکیج‌های پایتون دارد و در تصویر نهایی نمی‌ماند؛ تصویر نهایی روی `python:3.11-slim` فقط `chromium` (مسیر اصلی تولید PDF)، کتابخانه‌های pango (`libpango-1.0-0`، `libpangoft2-1.0-0`، `libharfbuzz0b`) برای پشتوانهٔ WeasyPrint، `libpq5` و فونت‌های `fonts-vazirmatn`/`fonts-noto-core` را نصب می‌کند. بنابراین تولید صورت‌حساب PDF داخل کانتینر کار می‌کند و به مرورگر یا فونت نصب‌شده روی میزبان نیازی نیست. اگر کانتینر با کاربر root اجرا شود، `PdfBrowser` خودش `--no-sandbox` را اضافه می‌کند (Chromium به‌عنوان root سندباکس را راه نمی‌اندازد)؛ روی کاربر عادی و روی ویندوز این فلگ اضافه نمی‌شود.

## قواعد و نکات توسعه

1. **مانده را ذخیره نکنید.** هر تغییر مالی باید در `services/balance.py` منعکس شود و تست داشته باشد.
2. **یک دفتر کل.** پرداخت از هر مسیری باید `POST /billing/payments/` را بزند؛ اندپوینت موازی نسازید.
3. **فایل‌ها قابل بازسازی‌اند.** تولید در `generation.py`؛ منطق ذخیره/انقضا در `files.py`. مسیر فایل را در مدل ذخیره نکنید مگر از طریق `FinalFile`.
4. **سرور توسعه با `--noreload`** بالا می‌آید؛ بعد از هر تغییر بک‌اند باید دستی ری‌استارت شود. اگر تغییرات را نمی‌بینید، اول همین را چک کنید.
5. **فرانت:** `npx tsc --noEmit` قبل از کامیت؛ بیلد production حدود ۵۰ ثانیه است. نوع‌ها را با `any` دور نزنید.
6. **متن‌ها فارسی و RTL** هستند؛ اعداد نمایشی با `to_persian_digits` و تاریخ‌ها با تقویم شمسی. در PDF/Word هم همین قواعد رعایت می‌شود.
7. **مجوز در سرور.** افزودن endpoint جدید بدون `@perm_required` ممنوع.
8. **کنتراست:** روی سطوح همیشه‌تیره `dark-surface` بگذارید؛ متن زیر ۳:۱ قابل قبول نیست (تست دستی با DevTools).
9. **مهاجرت‌ها:** پس از تغییر مدل `makemigrations` + `migrate` و کامیت فایل مهاجرت. هیچ‌وقت مهاجرت را دستکاری نکنید که روی دیتابیس مشتری اجرا شده باشد.
10. **Git:** ریموت `origin` = `github.com/myazdanpanah/KermanKhodroTravel` (شاخهٔ `main`)، ریموت `upstream` = Nexivo. شاخهٔ جاری توسعه `customer/kermankhodro` است و تغییرات با `git push origin HEAD:main` منتشر می‌شوند. ادغام آپ‌استریم باید با احتیاط و همراه با تست‌های مالی انجام شود (فایل‌های `generation.py`، `ERPLayout.tsx` و مدل‌های billing بیش از همه تعارض می‌گیرند).
11. **CRLF/LF:** مخزن روی ویندوز با `core.autocrlf` کار می‌کند؛ هنگام کامیت هشدار CRLF طبیعی است و نباید فایل‌ها را بازنویسی خطی کنید.

## کارهای باقی‌مانده / محدودیت‌ها

- ماژول‌های Nexivo (انبار، خرید، فروش، تولید، ترابر) برای این مشتری پیاده/آزمایش نشده‌اند؛ در لانچر پنهان‌اند.
- PDF بدون مرورگر به WeasyPrint برمی‌گردد؛ تصویر Docker هر دو مسیر را دارد (Chromium و pango)، پس نبود مرورگر در استقرار مستند رخ نمی‌دهد. اگر مرورگر موجود باشد ولی خطا بدهد، `GenerationError` فارسی ثبت می‌شود و PDF ساخته نمی‌شود — عمداً به WeasyPrint برنمی‌گردد.
- مسیر مرورگر روی مک در فهرست پیش‌فرض نیست؛ آنجا `PDF_BROWSER_PATH` لازم است.
- پایگاه‌داده جاری ERP به مجموعه داده‌های هوش تجاری (BI) و کلاینت Superset متصل است و در صورت بالا بودن کانتینر سوپرست، ثبت و همگام‌سازی کلاینت به‌صورت خودکار و امن انجام می‌شود.
- حذف تاریخچه (`can_delete_history`) و بازیابی/پشتیبان‌گیری درون‌برنامه‌ای باید قبل از استفاده روی دادهٔ واقعی آزمایش شود.
- تست‌های frontend وجود ندارند؛ بررسی‌ها با `tsc`، بیلد و آزمون دستی انجام می‌شود.
- ارسال واقعی پیامک در این محیط آزمایش نشده است؛ برای استفاده باید کلید/شمارهٔ فرستندهٔ معتبر در «تنظیمات پیامک» وارد و درگاه فعال شود. تست‌ها با mock ارائه‌دهنده اجرا می‌شوند.
- پیش‌نمایش XLSX برای کارایی فقط ۵۰۰ ردیف اول هر Sheet را نشان می‌دهد (کل فایل از دکمهٔ دانلود در دسترس است).

### گزارش‌ساز صورت‌حساب (PDF)

تنظیمات → **گزارش‌ساز** طراحی PDF صورت‌حساب‌هایی را که پس از ثبت بدهی صادر می‌شوند کنترل می‌کند. طراحی در `ReportDesign` (جدول `billing_reportdesign`) به‌صورت JSON ذخیره می‌شود و پیش از ذخیره اعتبارسنجی می‌گردد:

- عنوان قابل تنظیم با متغیرهای `{service_type}`، `{buyer_name}`، `{number}` و `{date}`
- برچسب و نمایش/عدم نمایش هر یک از ۹ ستون جدول
- تعداد سطر در هر صفحه (۱ تا ۲۰) و جهت کاغذ (افقی/عمودی)
- فونت (Vazirmatn / B Nazanin / B Titr)، رنگ خطوط و پس‌زمینه سرستون
- یادداشت بالای جدول، متن پایین صورت‌حساب، برچسب مهر
- نمایش لوگو، جمع هر صفحه، جمع کل، امضای مدیر و مهر

پیش‌نمایش زنده با داده نمونه در همان تب نمایش داده می‌شود. API: `GET/PUT /api/v1/billing/report-design/` و `POST /api/v1/billing/report-design/reset/` (تغییر فقط با مجوز `can_manage_settings`). تغییر طراحی روی صورت‌حساب‌های بعدی اثر دارد و فایل‌های قبلی دست‌نخورده می‌مانند.

### خروجی اکسل صورت وضعیت مشتریان

در صفحه **صورت‌حساب → عملکرد** یا پنجره کاردکس مشتری، دکمه «خروجی اکسل صورت وضعیت» یک فایل XLSX می‌سازد: در خروجی کلی همهٔ شرکت‌ها، شیت اول خلاصه وضعیت با بدهکار/بستانکار/مانده هر شرکت و شیت دوم ریز کل تراکنش‌ها است. در خروجی اختصاصی یک شرکت، برگهٔ اصلی و اول فایل اکسل مستقیماً شیت **ریز کامل اسناد و تراکنش‌های خط‌به‌خط** با فرمت‌بندی رسمی، ستون‌های مانده، شرح، تاریخ جلالی و شماره مرجع است. Endpoint: `GET /api/v1/billing/statements/excel/?payer=<code>`.

### گزارش‌ساز (ادیتور بصری A4)

تب **تنظیمات → گزارش‌ساز** یک ادیتور WYSIWYG واقعی است: بوم A4 با خط‌کش میلی‌متری، زوم، پنل «اجزا»، درخت «ساختار» (سربرگ/بدنه/پابرگ) و پنل تنظیمات صفحه/عنصر.

- کشیدن‌و‌رهاکردن هر بلوک، تغییر اندازه با دستگیره، جابه‌جایی با کلیدهای جهت (Shift = ۱۰mm)، Delete برای حذف، Ctrl-style undo/redo.
- ویرایش متن با دوبار کلیک روی خود متن (contentEditable) و پشتیبانی از متغیرها: `{service_type}`، `{buyer_name}`، `{number}`، `{date}`، `{grand_debt}`، `{grand_credit}`، `{grand_balance}`، `{page_debt}`، `{manager_name}`.
- اجزای قابل افزودن: متن، تصویر/لوگو، خط، مستطیل (با رنگ داخل)، فاصله‌گذار، جدول (برچسب/عرض/نمایش ستون‌ها و تعداد سطر در صفحه)، QR Code و بارکد (Code128، از داده‌هایی مثل `{number}`)، امضا و مهر.
- تنظیمات صفحه: جهت A4، فونت (Vazirmatn / B Nazanin / B Titr)، رنگ خطوط و سرستون، برچسب مهر.
- همان مختصات میلی‌متری در رندر سرور استفاده می‌شود؛ QR/بارکد در سرور با `qrcode` و `python-barcode` به تصویر تبدیل و داخل PDF جاسازی می‌شوند.
- طراحی قبلی (نسخهٔ ۱) هنگام خواندن به‌صورت خودکار به نسخهٔ ۲ (عناصر موقعیت‌دار) تبدیل می‌شود.

### صورت وضعیت اکسل با تفکیک بدهی و پرداخت

شیت «خلاصه شرکت‌ها» این ستون‌ها را دارد: صورتحساب، بدهی دستی، جمع بدهی، پرداخت، بستانکاری، مانده. هر شرکت یک شیت گردش جداگانه دارد که بالای آن جمع بدهی (صورتحساب + بدهی دستی)، جمع پرداخت‌ها، بستانکاری و مانده آمده و سپس ردیف‌های تاریخ‌دار (تاریخ شمسی) با ماندهٔ تجمعی.
